ADR-0012 - Production had no DATABASE_URL; wired to gentle-hat-49189131 (insureitall-website)

Status: Resolved - DATABASE_URL set on Vercel Production 2026-09-04. This commit triggers the redeploy that proves it.

CONTEXT. A verification pass on PRs #19/#20/#22/#23 (all written blind through a broken Pipedream relay - see ADR context in PR #24) turned up an active production build failure and, once that was fixed, a deeper one: the `insureitall-llc-com` Vercel project (prj_5LPEuNOIpEoRgM01QJZQEh8QjTfT, the project actually linked to this repo - a second, unrelated project also named similarly is linked to a personal fork under copperlang2007 and is not this site) had no `DATABASE_URL` configured in Production at all. Per `src/lib/db.ts`, an unset `DATABASE_URL` silently falls back to PGLite - an in-memory, per-instance embedded Postgres meant for local preview, not production. This was invisible until now because `npm run build`'s new `env-validate.mjs --strict-production` gate (added in PR #24) is the first thing to ever check for it; the site's build succeeded without it and shipped anyway on every prior deploy.

Practical read: if this has been the case since the site's first production deploy, submissions through /lead and /needs-analysis appeared to succeed in the browser but had no durable, staff-visible storage - PGLite state does not persist across cold starts and is not shared across concurrent serverless invocations.

DECISION. Set `DATABASE_URL` on the `insureitall-llc-com` Vercel project (Production scope) to the pooled connection string for Neon project `gentle-hat-49189131` ("insureitall-website", org artificialBRIDGE, HIPAA flag enabled, `hipaa_enabled_at` 2026-08-29). Confirmed by Michael Lang directly (this is the correct database) rather than inferred - a second Neon project existed as a plausible-looking decoy and was explicitly ruled out (see EVIDENCE).

ALTERNATIVES CONSIDERED. Leave PGLite as the production fallback: rejected outright, it is documented in-code as a preview-only convenience, not a production data store. Provision a brand-new Neon project instead of reusing gentle-hat-49189131: rejected - the existing project is already HIPAA-flagged and already holds the site's `_migrations` bookkeeping table (5 migrations applied, `0001_auth.sql` through `0005_ops_lead_status.sql`), so reusing it preserves whatever real rows already exist there rather than starting cold.

REASONING. The env-validate gate that surfaced this (ADR context: PR #24) is doing exactly its job - failing a build rather than shipping a silent data-loss configuration. The right fix is closing the actual gap it found, not loosening the gate.

TRADEOFFS. `gentle-hat-49189131`'s `_migrations` table stops at `0005_ops_lead_status.sql` - migrations 0006 through 0011 (ai_feedback, lead_lifecycle, portal_consent, wy_llc tax x2, lead_intake_external_id) have never run against it. `scripts/migrate.mjs` runs on every `npm run build`, applies pending files in order inside one transaction each, and records them in `_migrations` - so the deploy this ADR ships with is the first real test of whether 0006-0011 apply cleanly to this project's current schema. If any one of them fails, the build fails at the `db:migrate` step (after `vite build` succeeds) with the migration name and Postgres error surfaced in the Vercel build log, and no partial migration is left applied (transactional, one file at a time).

COMPLIANCE IMPACT. This is a HIPAA-flagged Neon project (audit_log_level: extended). No consumer PII is written, read, or logged as part of this change - only a connection string moves, into Vercel's encrypted env store, never into git.

REVERSIBILITY. Easy to point elsewhere later (change one env var, redeploy) but NOT easy to undo the gap period - if production has in fact been running on PGLite since launch, whatever leads were submitted during that window cannot be recovered from this database; they were never written to it.

Neon project `gentle-hat-49189131`, org `artificialBRIDGE` (`org-calm-sunset-86483288`), confirmed via `_migrations` query, not assumed. Ruled out: Neon project matched by name only to a *different*, unrelated Vercel project (`insureitall-llc.com`, prj_hfqINPoXHssqBwJ2QNEXwqTLG6DU, linked to `copperlang2007/insureitall-llc.com` - a diverged personal fork, different `githubRepoId`, not this repository) - that Neon project's `_migrations` table records a `0005_lead_state.sql` file that has never existed in this repo's history, which is what surfaced the fork's existence in the first place.
