ADR-0013 - TPMO disclaimer: retire the spliced/static "14 and 14" string for a generic interim form; land the bridge_disclosure resolver as staged, un-wired infrastructure

Status: Accepted (interim). The text change ships now. The numeric resolver does not go live until real appointment data exists and Ryan Butterfield (acting CCO) signs `docs/cco-confirmation.md`.

CONTEXT. Michael Lang supplied a compliance audit (`docs/audits/AUD-20260903-insureitall-llc.com.md`) and a companion engine (`tools/bridge-disclosure/`: schema, resolver, seed, 24-check acceptance suite) built to compute the CMS TPMO disclaimer per county from real carrier-appointment data. The audit found the live string in `src/lib/compliance.ts` was defective independent of any data question: it spliced the numeric standardized sentence ("Currently we represent N organizations which offer N products...") with a second sentence ("Any information we provide is limited to those plans we do offer...") that belongs to no version of 42 CFR 422.2267(e)(41) — standardized content is served verbatim, not recombined. Separately, the static count (14 organizations / 14 products) asserts a 1:1 org-to-plan ratio that does not occur in practice for an appointed FMO and has no source that would survive a carrier or CMS audit request; `docs/cco-confirmation.md` (the form meant to confirm or replace that count) is unsigned. The string also retains a State Health Insurance Program (SHIP) referral.

I independently verified the regulatory claims before touching shipped copy (this is regulated Medicare marketing content, not internal tooling): Cornell LII's current text of 42 CFR 422.2267 and the Federal Register confirm CMS removed SHIP from the standardized text and moved verbal-disclosure timing from "first minute" to "prior to the discussion of any benefits," in the CY2027 MA/Part D final rule (CMS-4208-F3/CMS-4212-F, RIN 0938-AV40, 91 FR 17384-17602 at 17583, doc 2026-06600, published 4/6/2026), effective for CY2027 marketing beginning Oct 1, 2026. Both post-amendment standardized forms (sells-all and does-not-sell-all) require the organization/product count blanks filled in — there is no CMS-verbatim "no-numbers" variant. The resolver's own README already flagged this as unconfirmed and I found no independent source that resolves it.

Validating the fix (`npm run typecheck` + a local Vite render of `/`, `/compare`, `/lead`) surfaced a third, independent copy the original grep-based audit missed: `src/lib/seo.ts`'s homepage FAQ ("Which carriers and plans do you offer?") hardcoded its own splice — "We do not offer every plan available in your area. Please contact Medicare.gov, 1-800-MEDICARE, or your local SHIP..." — feeding both the visible FAQ text and the page's FAQPage JSON-LD schema (i.e. also shipped to search engines and AI answer surfaces). This is exactly the F5 "two hardcoded copies, no single source" risk the audit warned about, just a third instance it didn't have visibility into. Fixed the same way: `HOME_FAQS` in `seo.ts` now interpolates `TPMO_DISCLAIMER` from `compliance.ts` instead of hand-duplicating it. Confirmed post-fix: zero occurrences of "SHIP" or "14 organizations" anywhere in the rendered `/`, `/compare`, `/lead` HTML.

DECISION. Three moves, not one:
1. `src/lib/compliance.ts` `TPMO_DISCLAIMER` now serves a single, unmodified, no-numbers sentence — the same one the resolver's fail-closed path serves (`v_generic_nonumbers` in `tools/bridge-disclosure/seed.py`) — with SHIP dropped. This is a stopgap, explicitly labeled `confirmed=0` in the resolver's variant table and in the code comment: it is the safer of the two available positions (no unmodified regulatory text, no unprovable number, no stale SHIP reference), not verified CMS standardized content, and it stays pending Ryan Butterfield's sign-off.
2. `src/lib/seo.ts`'s `HOME_FAQS` FAQ answer now interpolates `TPMO_DISCLAIMER` instead of hand-duplicating a fourth variant — closes the drift risk in both the visible FAQ and its JSON-LD schema.
3. The `bridge_disclosure` engine (schema.sql, resolver.py, seed.py, test_resolver.py, README.md) is landed at `tools/bridge-disclosure/` as staged infrastructure — tests pass (24/24) against its fixture data — but is NOT wired into the live site. There is no real `agency_appointments` feed, no ZIP/county capture UI on any page, and no Neon-backed deployment path for it yet. Wiring it now against fixture data would put a fabricated-looking but structurally real-seeming number in front of beneficiaries; that is a worse failure mode than the current generic sentence.

ALTERNATIVES CONSIDERED. (a) Correct "14 and 14" to a different static pair: rejected — fixes the implausibility, not the "unprovable" and "not area-specific" problems (findings F2/F3), and 42 CFR 422.2265 explicitly permits collecting ZIP/county instead of guessing a sitewide number. (b) Wire the resolver live today against a hand-entered or estimated appointment count: rejected — violates the resolver's own first rule ("fail closed... a wrong number is a violation, a generic disclaimer is not") and manufactures the appearance of verified per-county evidence where none exists. (c) Wait for Ryan's sign-off before changing anything: rejected — the splice (F1) is not a data question Ryan's authority governs, it's a citation-composition defect; leaving known-defective regulatory copy live while waiting on an unrelated sign-off is the worse risk.

REASONING. F1 is provably wrong regardless of what the correct count turns out to be, and needs no one's confirmation to fix. F2/F3 require real appointment data and county capture, which do not exist in this codebase yet; publishing any number without that data — old or new — is not a defensible interim. The generic sentence is safe under both the pre- and post-Oct-2026 regimes, so it also moots the SHIP-timing question (F4) for the interim period without needing to branch on the Oct 1 boundary in static site copy.

TRADEOFFS. The interim sentence's own CMS sourcing is unconfirmed (industry practice for anonymous pages, not verbatim regulation) — it is a defensible choice, not a verified one, and is called out as such everywhere it appears (code comment, resolver variant table, README, this ADR). It also drops the org/product count entirely, which is less specific marketing content than the (defective) status quo — acceptable because specificity built on an unprovable number is not an asset.

MASTER DATA FLYWHEEL / MOAT IMPACT. `tools/bridge-disclosure/` is the actual asset per its own README: a carrier-appointment normalization + evidence-chain layer that is hard to copy (per-carrier export adapters) and reusable across every artificialBRIDGE Medicare property, not just this one. Landing it now — tested, documented, not yet live — means the day a real `agency_appointments` feed exists, activation is a data-loading exercise, not a rebuild. `render_events` is a hash-chained audit trail (`verify_chain`) designed to become the compliance-evidence flywheel referenced in the global operating charter once live.

SECURITY / COMPLIANCE IMPACT. No PHI or beneficiary PII involved. This is public marketing copy under 42 CFR 422.2267(e)(41)/423.2267(e)(41) (TPMO standardized disclaimer requirements) and 42 CFR 422.2265 (permission to require ZIP/county entry, cited for the resolver's ambiguous-ZIP behavior). Regulatory citations above were verified live against Cornell LII and the Federal Register on 2026-09-05, not asserted from training memory.

REVERSIBILITY. Easy. The text change is a one-string edit in `src/lib/compliance.ts`; the resolver package is inert until something calls it. Reverting either is a single commit.
