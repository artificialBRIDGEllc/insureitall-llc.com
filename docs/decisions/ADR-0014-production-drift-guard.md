ADR-0014 - Production Drift Guard: detect a Vercel production deployment that silently regresses behind main

Status: Accepted.

CONTEXT. On 2026-08-27 the site's phone number was set to a wrong number (908-827-6223) and shipped to production. PR #30 (commit f07db04, 2026-09-09) fixed it to 813-742-6798, verified against `src/lib/utils.ts`/`seo.ts`, and deployed cleanly to production. On 2026-09-11 someone clicked "Redeploy" on a two-day-old row in the Vercel dashboard's Deployments tab — a normal-looking button on a deployment that happened to predate the fix (PR #29's commit, f75393f). That redeploy became the new production deployment and silently reverted the live phone number back to 908, with no failed check, no CI signal, no error anywhere: `main` branch was correct the entire time, so every code-level safeguard (tests, typecheck, `npm run debt:strict`) kept passing. The regression was only found when Michael reported the wrong number showing on the live site, three days later.

Nothing in this repo's CI (`.github/workflows/ci.yml`) can catch this class of failure — it verifies commits before merge, not what Vercel is actually serving after a human action in a dashboard neither `git log` nor GitHub Actions has visibility into.

DECISION. Add `scripts/production-drift-guard.mjs`, run on a schedule by `.github/workflows/production-drift-guard.yml` (every 15 minutes + manual dispatch), which:

1. Resolves the live deployment by the actual production **domain** (`www.insureitall-llc.com` — the host visitors land on; the apex 307-redirects here, so checking it directly rather than the redirector — via Vercel's `GET /v13/deployments/{domain}`, the same lookup a browser's request effectively triggers), not by a hardcoded project ID. A project-ID lookup only ever inspects the project you already assume is correct, so it can't catch the domain itself moving to a different Vercel project — a real, adjacent risk found during this investigation: a look-alike `insureitall-llc.com` project exists on the `copperlang2007` personal fork, in the same Vercel team.
2. Asserts that resolved deployment is `readyState: "READY"` (not mid-build or errored — a non-ready deployment can't be what's actually serving traffic and must never be trusted as a baseline), and that its `project.id` is the expected one (`prj_5LPEuNOIpEoRgM01QJZQEh8QjTfT`) and its `githubOrg`/`githubRepo` metadata is `artificialBRIDGEllc/insureitall-llc.com`.
3. Asserts that commit is actually in `main`'s history (`git merge-base --is-ancestor`) — catches a deploy from an unmerged branch.
4. Asserts that commit is a descendant of (or equal to) the last commit this guard verified. A prior commit — the exact shape of the Sep 11 incident — fails this check.
5. On pass, advances the baseline and exits 0. On failure, exits non-zero and the workflow files or updates a `production-drift`-labeled GitHub issue so it surfaces even if nobody is watching Actions runs; on the next pass, it closes that issue.

The baseline is seeded in this same change, checked into `.github/state/last-known-good-production-sha.txt`, at `f07db0418a0ae07909b0ec9662f89d0c3c0fb3ca` (PR #30's production deployment, the last commit independently confirmed correct) rather than bootstrapped from whatever is live when the workflow first runs — bootstrapping from "whatever's live now" would have silently accepted the still-broken Sep 11 state as correct. From there it advances entirely inside the GitHub Actions cache (`production-baseline-<run-id>`, restored by prefix), never committed back to `main`: committing the advancing SHA to the production branch would itself trigger a new Vercel deploy, which the guard would then need to verify, advancing the baseline again and pushing again — an unbounded deploy loop. The checked-in file remains as the permanent cache-miss fallback (first run ever, or after a 7-day cache eviction).

A first review pass (GitHub Copilot, on PR #32) caught four real gaps in the design above before merge: the project-ID-only lookup missing a domain move (fixed by #1), no `readyState` gate letting an in-flight deployment falsely advance the baseline (fixed by #2), the git-commit baseline creating the deploy loop described above (fixed by moving to Actions cache), and the issue-filing step's `if: failure()` being job-wide instead of scoped to the guard step itself, which would have filed false "production is down" incidents on an unrelated checkout/cache hiccup (fixed by gating on `steps.guard.outcome`).

A second review pass on the fix commit raised four more findings. Two were verified and fixed:
- The guard was checking the apex domain (`insureitall-llc.com`), which the site's own audit (`docs/audits/AUD-20260825-insureitall-llc.com.md`, lines 3 & 13) documents as 307-redirecting to `www.insureitall-llc.com` — checking the redirector isn't the same as checking what a visitor's browser actually renders. `PRODUCTION_DOMAIN` now points at `www.insureitall-llc.com`.
- `steps.guard.outcome == 'failure'` didn't distinguish "the guard found a real drift problem" from "the guard couldn't run at all" (no `VERCEL_TOKEN` yet, or a Vercel API/network error) — both would have filed the same "production is down" issue, which is actively misleading the day this ships, before the token secret exists. The script now exits `1` for an actual finding and `2` for a guard-error, and the workflow (capturing the numeric code, not just success/failure) files into two differently-labeled issues.

Two were investigated and are **not applicable**, kept here rather than silently dropped so the reasoning doesn't have to be re-derived later:
- *"The project identifier is `projectId`, not `project.id` — this expression is always undefined."* Checked against Vercel's own API reference for `GET /v13/deployments/{idOrUrl}`: "Additional details will be included when the authenticated user or team is an owner of the deployment," and the owner-authenticated response schema's `project` field is `{id, name, framework}` — `projectId` is a top-level field only in the reduced/non-owner schema variant. `VERCEL_TOKEN` is specified as a team-scoped token for this exact team, i.e. always an owner request. Confirmed empirically too: a live authenticated call against this project returned `project: {id: "prj_5LPE...", name: "insureitall-llc-com", framework: "tanstack-start"}` exactly as coded. Added `?? deployment?.projectId` as a zero-cost fallback regardless, in case token scoping ever changes.
- *"`withGitRepoInfo` defaults to `false` and gates the Git metadata this guard depends on."* Checked against the same API reference: `withGitRepoInfo` gates a separate `gitSource` object (ref/sha/repo, resolved live) — it says nothing about `meta`, which is a free-form string map Vercel populates from the build's git integration at deploy time regardless of query params. The same live call above returned a fully populated `meta.githubCommitSha`/`githubOrg`/`githubRepo` with no `withGitRepoInfo` param sent at all.

A third review pass found the guard-error split from round two was incomplete: `git rev-parse`, the baseline file read, and the baseline write all sat outside the try/catch that produced exit code 2, so any of them throwing fell through to Node's default uncaught-exception exit code (1) — read by the workflow as a real drift finding rather than "the guard didn't run." Widened the try/catch to cover the whole check, reserving exit 1 strictly for `evaluateDeployment`'s own findings; verified live with a deliberately-bad token (403), which now correctly exits 2. Also added a 20-second `AbortSignal.timeout` on the Vercel fetch (matching the existing pattern in `src/lib/bridget-console.ts`) — without it, a hung request could be killed by the job's 5-minute timeout before the catch block ever ran, dropping the incident with no issue filed at all. And the `production-drift-guard-error` issue had no close path once the guard started working again — added one, gated on the guard actually executing (exit 0 or 1), separate from the `production-drift` issue's close condition (exit 0 only).

A fourth review pass found: the PR description still said the baseline gets "committed" after round two moved it to the Actions cache — corrected. The citation for the apex-redirect claim (both here and in the code comment) pointed at the wrong audit file — `AUD-20260903-insureitall-llc.com.md` is the compliance-copy audit and contains no redirect information; the actual redirect is documented in `AUD-20260825-insureitall-llc.com.md` at lines 3 and 13 — fixed both citations. Most substantively: `gitIsAncestor`'s `catch { return false }` treated every `git merge-base --is-ancestor` failure as a valid "not an ancestor" answer, but git only uses exit status 1 for that; a different status (128, for an invalid object or corrupt repo — confirmed empirically against this repo) is a real git failure that must reach the guard-error path, not silently masquerade as a legitimate finding. Fixed to rethrow on any status other than 1. Also added the missing direct tests `fetchLiveDeployment` had never gotten despite exposing an injected `fetchImpl` (request construction, auth header, timeout, non-2xx handling) and two tests for `gitIsAncestor` against this repo's real git history — 9 → 13 tests.

One is accepted as a residual risk rather than fixed: the Actions-cache baseline is evicted after 7 days with no access, at which point restore silently falls back to the checked-in `f07db04` seed — if a rollback to some commit between that seed and wherever the baseline had actually advanced to happened during that same gap, it would pass both ancestry checks. In practice this needs the *entire workflow* to stop firing for a week (the cache is touched by every run, pass or fail, so a working schedule keeps it alive indefinitely) — i.e., the guard itself being down, which is a different, more visible failure (GitHub flags scheduled workflows disabled for repository inactivity, and Michael would notice the Actions tab going quiet). A fully closed fix needs a non-expiring external store (a Neon row, a repo variable written with elevated permissions) for what is a low-probability compound scenario; not building that now. Mitigation available at no cost: any time production is manually verified and promoted, updating `.github/state/last-known-good-production-sha.txt` in that same PR re-anchors the seed and closes the gap.

ALTERNATIVES CONSIDERED. (a) Vercel deployment protection / branch restrictions to block manual redeploys of old commits: not available on the current plan tier for this granularity, and would block legitimate emergency rollbacks. (b) A post-deploy smoke test that scrapes the live site for `813-742-6798`: fragile (couples infra monitoring to one page's copy, breaks the next time the number legitimately changes) and doesn't generalize to the next thing that regresses this way. (c) Polling less frequently (hourly/daily): rejected — this incident sat for 3 days; 15 minutes costs nothing on a scheduled Actions job and catches the next one same-day.

REASONING. The failure mode is specifically "production moved backward in history," not "production differs from main" (normal deploy lag is not an incident) and not "the phone number is wrong" (too narrow, doesn't generalize). Commit ancestry is the right invariant: cheap to check, generalizes to any regression this shape of accident could cause, and needs no knowledge of what changed.

TRADEOFFS. Requires a `VERCEL_TOKEN` repo secret (read-only Vercel API token) that does not yet exist — this is the one manual setup step, tracked below. The guard also can't stop the click from happening again; it shortens detection from "whenever a customer/founder notices" to at most 15 minutes, and gives a named, evidenced GitHub issue instead of silence.

MASTER DATA FLYWHEEL / MOAT IMPACT. Reusable pattern, not INSUREitALL-specific: any Vercel-deployed artificialBRIDGE property with a `githubCommitSha`-bearing deployment can adopt the same script by changing the four exported constants (team/project IDs, expected org/repo). Candidate for promotion to a shared `build-mode`/`aws-ops-engineer`-adjacent checklist item across the estate.

SECURITY / COMPLIANCE IMPACT. None directly — no PHI/PII touched. Indirectly closes a compliance-adjacent gap: a wrong published contact number is a beneficiary-trust and TPMO-adjacent concern (the number is the disclosed point of contact throughout `src/lib/compliance.ts` copy).

REVERSIBILITY. Easy. Disable by turning off the workflow or deleting it; no runtime behavior of the site itself is touched.

EVIDENCE. Vercel deployment history for `prj_5LPEuNOIpEoRgM01QJZQEh8QjTfT` (deployments `dpl_Hz7NcDJtg8Yn6iGf2j7SCt1FkCQh` → `dpl_2GawHLGq5Qbnh1LPqXkgZsXhFANJ` → `dpl_3XAUYgzHfuk8NCfHdTEMhmQttCW3`, the last one a `"action": "redeploy"` of the first, timestamped after the second). `git log` on `main` showing `f07db04` (phone fix, merged) with zero remaining "908" occurrences in the tree. Live-verified `GET /v13/deployments/insureitall-llc.com` and `.../www.insureitall-llc.com` both resolve to `dpl_2GawHLGq5Qbnh1LPqXkgZsXhFANJ` (commit f07db04) as of this writing — production has since been promoted back to the fix. Vercel API reference, `GET /v13/deployments/{idOrUrl}` (fetched 2026-09-14): owner-authenticated response schema for `project` (`{id, name, framework}`) and the `withGitRepoInfo` parameter description (gates `gitSource`, not `meta`). `scripts/production-drift-guard.test.mjs`, 13/13 passing (including real-git-history tests for `gitIsAncestor`'s exit-code handling and injected-fetch tests for `fetchLiveDeployment`'s request construction and error handling).
